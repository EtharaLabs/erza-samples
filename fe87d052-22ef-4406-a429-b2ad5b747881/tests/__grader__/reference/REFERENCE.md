# Reference answer

The copy carried seven distinct causes: five change result bits and two change only the cost of conversion. Cause 7 is inherited unchanged from fast_float 8.3.3 as released; it is a genuine nonconformance with the contract and counts as a reference cause like the others. Its helpers carry renamed identifiers and its comments were removed; the names below are the copy's. A report need not find all of them to satisfy a criterion; each criterion says what it requires of the causes the report claims. A claimed cause that describes one of these causes at a finer grain, in other words, or through one of its symptoms, counts as that cause.

1. The exact-halfway test in `nearest_binary` (`include/fast_float/decimal_to_binary.h`, the 128-bit product step) tested `(answer.mantissa & 1) == 1` where the base tests `(answer.mantissa & 3) == 1`. An exact tie whose lower neighbour has an odd significand was rounded down instead of to even. Reproducing inputs: `double 3786351887433356.75` requires `0x432AE7557E7D7D1A`, the copy gave `0x432AE7557E7D7D19`; `float 22626205433856` requires `0x55A4A098`, the copy gave `0x55A4A097`.
2. `binary_format<float>::min_exponent_round_to_even()` (`include/fast_float/float_common.h`) returned -4, the binary64 value, where binary32 needs -17, so binary32 exact ties with a decimal exponent from -17 to -5 skipped the tie test and rounded up. Reproducing input: `float 0.6982338134765625e4` requires `0x45DA32B4`, the copy gave `0x45DA32B5`.
3. `binary_format<double>::max_mantissa_fast_path()` (`include/fast_float/float_common.h`) returned `uint64_t(4) << mantissa_explicit_bits()`, 2^54, where the base returns 2^53, so binary64 mantissas above 2^53 took Clinger's fast path (`exact_small_product`) and were rounded twice. Reproducing input: `double 15446755860161931e-8` requires `0x41A269F9CD340772`, the copy gave `0x41A269F9CD340773`.
4. The overflow clamp at the end of `nearest_binary` tested `answer.power2 > binary::infinite_power()` where the base tests `>=`, so a result landing on the infinite exponent with a non-zero fraction was packed as a NaN while `ec` still reported `std::errc::result_out_of_range`. Reproducing input: `double 1.798e308` requires `0x7FF0000000000000` with `result_out_of_range`, the copy gave `0x7FF000B2FDC560A6`.
5. Cost, no bit changes. For an input with more than 19 significant digits, `from_chars_advanced` (`include/fast_float/parse_number.h`) compared the rounded result for the truncated significand from `nearest_binary` with the result for the significand plus one from `scaled_binary` where the base uses `nearest_binary` for both, so the two never agreed and every such input within the power-of-ten table's range took the arbitrary-precision path (`exact_compare`), even when the 128-bit product decides it. Results stay correct; the instructions executed grow by about 2 to 3.5 times on such inputs. Affected input: any long input the product decides, for example `double` `6.83941199975692349231310104239542605453707329827661608465236342102926307944427328678732e-300`.
6. Cost, no bit changes. In `load_significand` (`include/fast_float/digit_comparison.h`, the big-integer path), the check for non-zero digits after the last one loaded ran `has_nonzero_digits(p, pend)` from each eight-character step to the end of the input instead of once, so its work grew with the square of the input length. Results stay correct; four times the length cost about 16 to 30 times the instructions. Affected input: a long input that reaches the big-integer path with a long run of trailing zeros, for example `double` `402752343221584.34375` followed by 8000 zeros.
7. Inherited from fast_float 8.3.3, unchanged in the copy. While parsing an explicit exponent, `parse_number_string` (`include/fast_float/ascii_number.h`) stops accumulating its digits once the magnitude reaches `0x10000000` (2^28) and only then adds the digit-position offset, so for an input with about 2^28 or more significant or fractional digits the offset can cancel a saturated exponent and the result is computed from a wrong exponent. Reproducing input: `double` `0.` followed by 268435455 zeros and `1e2684354560` (268,435,469 characters) requires `0x7FF0000000000000` with `result_out_of_range`, the copy gave `0x3FF0000000000000` with `std::errc()`. A report may give this reproduction in full, abbreviate it, or describe it.

Interactions between causes (the known ones; any one, stated in substance, is an interaction the reference answer accepts):

- Cause 3 hid cause 1 on integer ties: with the fast path widened, integers such as `9007199254740995` were rounded by the hardware conversion and came out right, so repairing cause 3 alone made those inputs wrong through cause 1.
- Causes 1 and 2 overlap on binary32 ties: with both present, binary32 ties rounded down in one exponent window and up in another, so repairing cause 1 alone left binary32 ties with exponents from -17 to -5 wrong.
- Cause 5 hid causes 2 and 4 on long spellings: it sent long inputs to the exact arbitrary-precision path, which rounds them correctly, so long spellings of binary32 ties and of values near overflow came out right, and repairing cause 5 alone exposed causes 2 and 4 on those spellings.

A statement that two causes do not interact is contradicted by the reference answer only when the pair appears in the list above.

Related facts (true, but not interactions between causes):

- Cause 4 split the value from the error code: `ec` was right while the value was a NaN, so a check on `ec` alone, or a patch that rewrote NaN to infinity at the call site, hid it.
- Short and long spellings of the same value take different paths (the 128-bit product step or Clinger for at most 19 significant digits, the comparison of two candidates and then the arbitrary-precision path beyond), so a cause could appear for one spelling and not the other.
- `integer_times_pow10` shares `nearest_binary` and Clinger's fast path with `from_chars`, so causes 1 to 4 also changed its results, and a repair placed only in `from_chars` does not reach it.
- Causes 5 and 6 change no bit pattern, so a report gives for each of them an affected input and the property it breaks, not a required or produced bit pattern; a repair that routes doubtful inputs to the arbitrary-precision path corrects causes 1 to 4 but breaks the cost bound.

Rejected claim classes (each is not one of the seven causes; a report asserting one as a cause claims something that is not a reference cause):

- that the contract permits or requires rounding ties away from zero, or that ties go to the lower neighbour;
- that digits beyond the 19th may be ignored or truncated, or that the result may depend on how many digits are written;
- that `result_out_of_range` should leave the value unmodified, or that a value too large should store the largest finite value;
- that a non-zero subnormal result is out of range;
- that converting to `double` first and then to `float` is correct for `float`;
- a cause located in the pattern matching or digit scanning of `ascii_number.h` (cause 7, the exponent saturation, is the only cause in that file), in the big-integer arithmetic of `bigint.h`, or in the power-of-five table of `fast_table.h`.
