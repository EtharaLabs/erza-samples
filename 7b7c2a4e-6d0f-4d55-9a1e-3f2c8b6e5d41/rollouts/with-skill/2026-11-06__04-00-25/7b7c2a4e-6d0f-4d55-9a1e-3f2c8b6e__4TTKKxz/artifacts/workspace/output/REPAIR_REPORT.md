# Raft repair report

The repair changes `raft.go` and `rawnode.go`, preserves the exported API and module files, and retains asynchronous storage processing. Ten regression tests are in `safety_regression_test.go`. No interaction traces or existing tests were changed.

## 1. Responses bypassed outstanding asynchronous persistence

**Verified by running code.** Violates election safety and state machine safety. The same routing error also prevented progress for an asynchronous singleton with PreVote.

`needStorageAppendMsg` checked only the current Ready's new writes. After an earlier Ready handed writes to the append thread, a duplicate request could produce another response without any new writes. That response went directly to the network, bypassing the earlier queued write. Self-addressed responses on this path were discarded.

Election schedule (A, B, C start at term 1):

1. A campaigns in term 2 and persists its own vote.
2. B receives A's vote request. B takes Ready, queuing its term/vote write without processing it.
3. Deliver the same request again. The original library sends B's second affirmative response immediately.
4. A receives it and becomes leader in term 2.
5. Crash B, losing its queued write. Restart B in term 1.
6. C campaigns in term 2. B persists a vote for C. C becomes the second leader in term 2.

Regression: `TestAsyncDuplicateVoteDurabilityRegression` detects both leaders.

State machine schedule:

1. A leads term 2; index 2 is committed everywhere.
2. A proposes X at index 3. B receives the append and queues persistence. Deliver the append again before B processes its queue.
3. B's duplicate acknowledgement escapes. A persists X, counts B, commits and applies X.
4. Crash B before its queued write. Isolate A.
5. C wins term 3 with B, both lacking X. C commits and applies its new leader no-op at index 3, conflicting with A's applied X.

Regression: `TestAsyncDuplicateAppendDurabilityRegression` detects the conflicting applications.

Singleton schedule: campaign on a singleton with AsyncStorageWrites and PreVote. Its self-directed pre-vote response requires no new write, so the original routing discards it. Draining every queue never completes the election. Regression: `TestAsyncSingletonPreVoteProgressRegression`.

**Repair:** generate a FIFO append-thread message whenever `msgsAfterAppend` is nonempty, including messages with no new writes. Its responses wait behind prior storage work, and self-directed responses are delivered.

## 2. Append responses supplied fictitious read confirmations

**Verified by running code in both storage modes.** Violates linearizable reads.

The leader treated any remote MsgAppResp, including an old response, as acknowledging the most recent outstanding read context. The response did not carry that context and could predate the read entirely.

Schedule:

1. A leads term 2 and has committed/applied through index 2.
2. Replicate an additional entry to B and C, holding B's term-2 append response and preventing acknowledgements from reaching A.
3. Isolate A. B and C elect C in term 3. C commits and applies through index 4.
4. Issue a ReadIndex request at A, after C has applied index 4. A records its stale commit index 2.
5. Deliver B's held term-2 append response. The original A counts B as confirming the new read, combines it with its own acknowledgement, and returns ReadState index 2.

Regression: `TestDelayedAppendCannotConfirmReadRegression` checks the returned index against the highest applied index at request issuance.

**Repair:** append responses no longer confirm reads. Safe reads use heartbeat responses carrying the read context that was actually sent to the peer.

## 3. Snapshot installation overtook the independent apply thread

**Verified by running code.** Violates applied-once, increasing application order.

Snapshots are installed by the append thread. Committed entries are applied by a different thread. FIFO ordering within either thread does not order those two operations.

Schedule:

1. A follower persists committed entries 2 and 3, hands them to its apply thread, and delays that thread.
2. Deliver a valid newer snapshot covering index 5, whose last entry is absent from the follower's log.
3. Process the append thread first. The original library installs the snapshot, applying through index 5.
4. Process the previously queued apply work. It applies index 2, then 3, repeating indexes covered by the snapshot and moving backwards.

Regression: `TestSnapshotWaitsForApplyThreadRegression`.

`TestCompactedSnapshotRetryRegression` verifies the same failure using an elected leader, real proposals, Storage.CreateSnapshot, compaction, and a snapshot generated by the library. On the repaired library it also checks that a rejected snapshot is retried successfully and that a subsequent proposal applies on every node without restarting the lagging follower.

**Repair:** reject a snapshot requiring log replacement while `applying > applied`. The leader can retry after outstanding application completes. The matching-log fast path, which only advances commitment, remains available.

## 4. One apply completion acknowledged every outstanding batch

**Verified by running code, including a partial-repair experiment.** Together with snapshot installation, violates applied-once/in-order application.

MsgStorageApplyResp processing advanced `applied` to the current `applying` watermark instead of the last entry in the completed message.

Schedule:

1. Hand separate committed batches ending at indexes 2 and 3 to the apply thread.
2. Apply only batch 2 and deliver its response, leaving batch 3 queued.
3. The original library reports applied=3 even though only index 2 has completed. `TestApplyResponseTracksCompletedBatchRegression` directly detects this false completion.
4. Deliver a snapshot covering index 5 and process the append thread. A snapshot guard based on the false watermark permits installation.
5. Apply queued index 3 after the snapshot, repeating covered state.

Regression: `TestSnapshotWaitsForExactApplyCompletionRegression`. This test also failed when running with the snapshot guard installed but the old apply-response code restored; the log is `snapshot-gate-only.log`.

**Repair:** advance application using the last index in the response's own entries. Existing monotonic handling accommodates delayed earlier completions.

## 5. Mixed election options could strand a healed node

**Verified by running code in both storage modes.** Violates eventual cluster-wide progress after healing.

A node responded to lower-term append/heartbeat messages only if its own PreVote or CheckQuorum was enabled. This ignored the sender's configuration.

Schedule:

1. A leads term 2. A and B enable CheckQuorum; C disables both CheckQuorum and PreVote.
2. Isolate C and campaign there, persisting term 3 without electing it.
3. Heal the network. A and B continuously exchange heartbeats, maintaining A's lease.
4. C silently discards A's lower-term heartbeats/appends. A and B ignore C's higher-term vote requests while their lease is active.
5. Repeated ticks and ordered delivery let A and B apply proposals, while C repeatedly raises its term and cannot catch up.

Regression: `TestMixedElectionOptionsCatchUpRegression`. This failure was also discovered in the mixed-option seeded simulation.

**Repair:** always send the existing higher-term append response to a stale append/heartbeat sender, regardless of the recipient's election options. This informs the leased leader that it must step down.

## Repair dependencies

- Election safety requires the persistence barrier in cause 1. State machine safety likewise depends on that barrier, including both vote responses and append acknowledgements.
- Applied-once/in-order application requires **both causes 3 and 4 repaired together**. The snapshot guard alone trusts an incorrect completion watermark; the exact watermark alone does not order the two threads. This dependency was verified with the partial-repair experiment.
- Linearizable reads require cause 2's fresh quorum evidence and the election/log safety preserved by cause 1. Removing the append-response shortcut alone does not repair unsafe elections or lost committed entries.
- Progress requires preserving self-directed responses (cause 1), retrying snapshots after application drains (causes 3–4), and informing stale leaders in mixed configurations (cause 5).

These dependency conclusions follow from the code and the reproduced schedules. They are not an exhaustive formal proof over every possible schedule.

## Validation

**Verified by running code:**

- The original full Go suite passed before edits.
- All ten named regression tests were run separately against the original production files; each failed. Names, exit statuses, and build-inclusive durations are recorded in `original-test-results.json`, with individual failure logs beside it.
- The repaired full suite passes with `go test ./... -count=1`, including the exact interaction traces without regeneration.
- `TestAdversarialSchedulesRegression` runs 800 seeded schedules, each with 300 adversarial steps, followed by a connected recovery phase requiring a fresh proposal on every node. It includes both storage modes, uniform and mixed election/storage options, campaigns, crashes, loss, duplication, reordering, delayed storage work, and read checks. Snapshot/compaction schedules are tested separately.
- The simulator checks leaders per term, conflicting applications across nodes/restarts, application ordering, and read-index lower bounds. It models durable storage separately from queued thread work and discards unprocessed local work on crashes.
- The regression binary's build and aggregate CPU timing are in `build.log` and `regressions-fixed.log`; the aggregate regression runtime is below the per-test ten-second CPU limit, and build time is below 120 seconds.

**Inferred without exhaustive execution:** restoring these durability, completion, and quorum-evidence invariants prevents the corresponding failure classes under other schedules. The finite simulations are regression evidence, not an enumeration of all possible clusters or executions.
